# dsh-visualize growth and promotion research

Research date: November 17, 2026 (Beijing time). Sources include the author's GitHub repositories, personal website, blog, and public talk materials, plus the GitHub API, official npm registry/download APIs, and community directories. Metrics are snapshots from the time of lookup.

## Findings and limits

At lookup, `Nagi-ovo/dsh-visualize` had **346 stars and 10 forks**. The current repository was created on August 13, 2026, and last pushed on November 15. The author prepared demo videos, social artwork, bilingual documentation, and directory cards early, then established installation through npm, GitHub, and a community plugin-management UI while maintaining host compatibility. Evidence also confirms promotion through another project, a dedicated blog page, and public slides introducing the plugin at a DSH community meetup. **These acquisition and conversion practices are reusable, but public evidence cannot quantify how many stars each contributed.** [Repository metadata](https://api.github.com/repos/Nagi-ovo/dsh-visualize)

The public history contains 65 commits beginning on August 8, 2026. The current repository was created after the earliest commit, and the history includes a repository-move commit. August 13 therefore cannot simply be treated as the product launch date. [Commit history](https://github.com/Nagi-ovo/dsh-visualize/commits/main/)

This research did not obtain GitHub traffic/referrer data, the author's platform analytics, paid advertising records, or a complete verifiable star timeline; the anonymous stargazer-timestamp request returned 401. It cannot attribute more than 300 stars to a particular post, directory, or feature release. Directory invitations and automated listings also do not necessarily demonstrate proactive marketing by the author.

## Evidence of cross-promotion

The strongest evidence of promotion through an author-controlled channel is the same author's [Nagi-ovo/dsh-ads README](https://github.com/Nagi-ovo/dsh-ads/blob/main/README.md). Its “Free ad space” section calls dsh-visualize “the only serious advertisement in this README” (translations) and links `assets/visualize-demo.webp` to `assets/visualize-demo.mp4`. Its ad system rotates public plugins tagged `dsh-plugin` and updated within two weeks; submission instructions allow custom copy/images through PRs. [Submission instructions](https://github.com/Nagi-ovo/dsh-ads/blob/main/contrib/README.md)

The corresponding [contrib/dsh-visualize.json](https://github.com/Nagi-ovo/dsh-ads/blob/main/contrib/dsh-visualize.json) uses the following copy, translated here into English:

```json
{
  "repo": "Nagi-ovo/dsh-visualize",
  "headline": "The model draws your interface directly",
  "sub": "Interactive cards appear in the conversation instead of a pasted code snippet",
  "badge": "Highly recommended",
  "button": "Install now",
  "palette": 2
}
```

This confirms cross-promotion through a second plugin and deliberate use of a short headline, benefit statement, call to action, and animated demo. The README also describes a “verification fix” that queries GitHub stars after a user clicks. Its `SELF_SLUG` points to `Nagi-ovo/dsh-ads` itself, so this mechanism is not evidence of stars gained by dsh-visualize. [Implementation](https://github.com/Nagi-ovo/dsh-ads/blob/main/src/index.ts)

## Current gaps and priorities

We already have unit tests and cross-platform CI; clearer gaps are public demonstrations, distribution, and discoverability. ## Lessons for reply-with-images

These recommendations adapt the practices above; they do not promise the same star count.

1. **Publish a real DSH demonstration.** Use owned, clearly licensed, or publicly reusable images to record a short sequence: question → search → inline images → images still readable after restart. Put an actual answer screenshot near the README top with a video link. Keep the static layout preview clearly distinguished from full session verification.
2. **Lead with the result.** An English opening could say, “Add real images to DeepSeek Harness answers, inline with the text and saved with the conversation.” Follow it with a recognizable task such as plant comparison or travel planning, then explain implementation, sources, and persistence. Model tool use and provider access remain conditional; avoid promising images in every answer or universal network availability.
3. **Shorten the installation path.** Verify real Desktop/Web installations and the tested host range before publishing to npm or downloadable GitHub Releases. Offer UI steps, one command, and a verification prompt. Requiring clone/build/pack loses non-developer users.
4. **Complete ecosystem metadata.** Add missing repository/homepage/bugs fields to package.json, prepare a distinct icon, GitHub topics, and English documentation, then follow each community directory's rules. Label community channels accurately.
5. **Share task-based examples regularly.** Organize examples around three real questions and show clear text fallback when a source is unavailable. Describe concrete improvements in releases rather than focusing only on coverage and internal architecture.
6. **Use conversion data for later decisions.** After publishing, record release/share dates, README views/clones where available, npm downloads, and issue feedback. Compare aligned timelines before claiming a channel works. Stars indicate interest; successful installation and retention are closer to product value.
7. **Use transparent cross-promotion.** If we later maintain another demo/tool plugin, include a short reply-with-images demo clearly labeled as a community recommendation, or submit to directories/rotations that accept contributions. Avoid copying the suggestive star-checking “verification fix” mechanism or treating impressions/clicks as evidence of star growth.

## Claims the evidence cannot support

Searches across X, Linux.do, Bilibili, WeChat, V2EX, and other public channels found no verifiable original promotional post. A Reddit “Built Visualizer” result belonged to a different dsh-visualizer project and was excluded. No reliable evidence was found for paid advertising, a viral post generating substantial stars, or purchased stars.

An undiscovered marketing activity must not be described as something that never happened. Confirming promotion on Weibo, Xiaohongshu, Bilibili, X, Reddit, or community groups requires original posts from the author's account with dates and links; third-party SEO directory pages alone are insufficient.
